# 技能清单与模板（10 个 SKILL.md，可直接复制使用）

> 用法：在工程里建 `skills/<名字>/SKILL.md`，把下面「模板」整段粘进去。
> 调用：DSH 里直接说「用 `lowpoly-asset` 检查这张桌子」；Qoder / WorkBuddy / Meoo 没有技能目录，把同一个 SKILL.md 内容贴进对话开头即可。
> 真相：Skill 只是提示词包，**不会替你编译、调试、渲染**。它的价值是把「你反复交代的话」固化下来。

## 1. `godot-gdscript` —— 写 GDScript 的规矩

**什么时候用**：任何改 `.gd` 文件的日子（全项目约 40% 的天数）。

**用法**：先说「按 godot-gdscript 规范改 `player.gd`」。

**缺点**：模型仍会编造不存在的方法（比如 4.x 删掉的 API），必须让它贴官方文档链接或自己跑一次。

**模板**
```markdown
---
name: godot-gdscript
description: 写或修改 Godot 4 GDScript 时使用，保证类型、信号、生命周期写法一致。
---

## 何时用
任何 .gd 文件的新建或修改。

## 必须遵守
1. 全部变量、参数、返回值写静态类型；不写 var x = 3。
2. 节点引用一律 @onready var x: Type = $Path，不用 get_node 字符串。
3. 信号命名 past_tense（如 opened），不用 on_open。
4. 生命周期：_ready 只做初始化，_process 里不放查找节点。
5. 跨场景通信走 EventBus 单例，不直接连别人的节点。
6. 禁止在 _process 里 new 对象或 load()。

## 输出要求
- 只给改动的函数，不重贴整个文件。
- 每个新 API 后面注明「Godot 4.7 文档：<章节名>」。
- 改完列出「这次可能影响的场景/脚本」。
```

## 2. `godot-scene-arch` —— 场景树与工程结构

**什么时候用**：新建场景、拆脚本、决定「谁管状态」的时候（约 8 天）。

**缺点**：容易给出过度设计的架构（ECS、事件总线套娃），对 6 个月的项目是负担。

**模板**
```markdown
---
name: godot-scene-arch
description: 规划 Godot 场景树与脚本职责，避免单场景膨胀和循环依赖。
---

## 何时用
新建 .tscn、拆分脚本、评审工程结构。

## 规则
1. 场景根节点承担「装配」，脚本挂在具体功能节点上，不写 god→do 的大脚本。
2. 一个场景最多 1 个脚本直接读写 GameState，其余用信号。
3. 场景之间不互相 get_node，跨场景只走 EventBus。
4. 目录：scenes/{world,buildings,characters,ui}，scripts/{core,player,npc,systems,minigames}。
5. 新增单例前先问：能不能用已有单例 + 信号解决？

## 输出
- 一张树形图（缩进列表即可）+ 每个节点的职责一句话。
- 标出「未来可能成为性能瓶颈」的节点。
```

## 3. `lowpoly-asset` —— 低模规范

**什么时候用**：建模、导入、检查面数的日子（约 15 天）。

**缺点**：只给规范，不给审美；它检查不出「这个模型丑」。

**模板**
```markdown
---
name: lowpoly-asset
description: 低多边形资产的面数、贴图、命名与导入规范。
---

## 硬指标
- 道具 ≤300 tri；建筑单栋 ≤25k tri；人物 800–1500 tri。
- 所有资产共用 1 张 512×512 调色板图集，不单独出贴图。
- 每场景 ≤4 个材质球。
- 命名：sm_ 前缀（sm_desk_a），贴图 t_，材质 m_。

## 检查清单
1. 面数是否超？超了先减面，不加 LOD。
2. UV 是否全在图集内？有无拉伸？
3. 原点是否在底部中心？（便于摆放）
4. 是否有 ngon？导出前三角化。
5. 碰撞体是否另做（不用渲染网格当碰撞）？

## 输出
- 逐条打勾，不通过项给出「怎么改」的具体操作。
```

## 4. `blockbench-model` —— 建模步骤

**什么时候用**：手搓课桌、椅子、墙、窗的周六（约 10 天）。

**缺点**：它不懂你的审美，也不懂照片里的比例，只保证流程不出错。

**模板**
```markdown
---
name: blockbench-model
description: 用 Blockbench 做低模道具的标准步骤与导出参数。
---

## 步骤
1. 先看参考照片，写下 3 个尺寸（长/宽/高，单位米）。
2. 用 Cube 起主体，比例对再加减细节；不要一上来做倒角。
3. 图集：新建 512×512，从色板取 6–8 个颜色，直接填色不画纹理。
4. 检查原点、朝向（-Z 朝前）、缩放（1 单位 = 1 米）。
5. 导出 GLB：+Y up，不导出相机灯光，应用缩放。

## 禁止
- 不用细分、不用布尔运算、不做倒角（低模不需要）。
- 不超过 300 tri 还继续加细节。

## 输出
- 导出文件名 + 面数 + 材质数，三项都要报。
```

## 5. `dialogue-json` —— 对话与任务数据

**什么时候用**：定 schema、写对话、改 JSON（约 12 天）。

**缺点**：字段一改就全库失效，必须配校验器；它自己不会跑校验。

**模板**
```markdown
---
name: dialogue-json
description: 对话与任务 JSON 的 schema、命名和校验规则。
---

## schema 要点
- 节点：id / speaker / text / next[] / conditions[] / effects[]
- 条件：{type:"quest", id:"q1", state:"active"} 这类结构化对象，不用字符串表达式。
- 效果：{type:"give", item:"rubber", n:1}
- 所有 next 必须指向存在的 id；叶子节点 next 为空数组。

## 规则
1. 一个 NPC 的对话放一个文件，文件名 = npc_id.json。
2. 文本里的梗、书名先查 IP 改名表。
3. 每条分支必须有出口，禁止悬空。

## 输出
- 先给 schema，再给 2 个示例节点，最后给「需要人工确认的 3 处」。
```

## 6. `narrative-branch` —— 支线结构

**什么时候用**：写三条支线、NPC 人设、每日事件（约 10 天）。

**缺点**：产出套路化（目标-阻碍-转折-奖励），需要你改写开头和结尾。

**模板**
```markdown
---
name: narrative-branch
description: 设计校园支线任务的结构与节奏。
---

## 结构（每条支线必须齐）
1. 钩子：玩家为什么现在要做（一句话，靠场景触发不靠 NPC 喊）。
2. 目标：可验证的完成条件（不是「了解一下」）。
3. 阻碍：至少 1 个机制阻碍（时间/空间/规则/人）。
4. 转折：中段一个意外，改变目标或代价。
5. 奖励：道具/数值/称号，必须与剧情相关。
6. 独占内容：这条线才有的场景或机制（没有就删掉这条线）。

## 校园口味
- 时长 8–15 分钟；不用战斗解决；用「被发现」「时间到」「老师来了」制造压力。

## 输出
- 200 字以内梗概 + 分步骤表（步骤/触发/完成条件/失败条件）。
```

## 7. `net-debug` —— 联机排查

**什么时候用**：W7–W9、W14、W20 的联机与网络相关日（约 12 天）。

**缺点**：只能给排查顺序，不能替你抓包；没有日志它就是在猜。

**模板**
```markdown
---
name: net-debug
description: Godot 高层多人游戏的同步问题排查顺序。
---

## 排查顺序（不要跳步）
1. 先确认「谁权威」：这个状态由房主算还是各端算？
2. 看日志：有没有 rpc 调用、参数对不对、peer_id 是谁。
3. 判断是「没发」「发错人」「收到但没应用」三种里的哪一种。
4. 只有确认是延迟/抖动，才去改插值或预测。

## 常见错觉
- 「不同步」经常是两端场景加载顺序不同，不是网络。
- 「卡顿」经常是 _process 里做查找，不是带宽。
- 「掉线」经常是 host 切场景时把 peer 踢了。

## 输出
- 先要日志，再给假设；每个假设给一条验证命令。
```

## 8. `playtest-report` —— 测试反馈整理

**什么时候用**：每次自测、内测、收反馈（约 15 天）。

**缺点**：会把「玩家说不好玩」翻译成技术问题，丢掉真实的体验判断。

**模板**
```markdown
---
name: playtest-report
description: 把试玩记录整理成可执行的 issue 清单。
---

## 分类
P0 崩溃/卡死/存档丢失；P1 功能不可用；P2 体验受损（迷路、看不懂）；P3 文案/细节。

## 每条 issue 必须包含
现象 / 复现步骤（3 步内）/ 期望 / 实际 / 影响人数。

## 输出
- 先给 P0/P1 表，再给 P2 归并后的「3 个体验主题」。
- 最后写一句「如果只能修 5 个，修哪 5 个」。
```

## 9. `scope-guard` —— 砍需求

**什么时候用**：想加系统、进度落后、每周复盘（约 8 天）。

**缺点**：你大概率会无视它的结论；它的价值只是让「砍」变得有依据。

**模板**
```markdown
---
name: scope-guard
description: 评估新需求是否该进当前版本，给出砍单建议。
---

## 打分（每项 0–2）
- 是否服务核心循环（上课/校园日常）？
- 是否 3 天内能做完？
- 是否已有系统能覆盖 80%？
- 是否有玩家明确要求？

## 结论
- ≥6：进当前版本
- 4–5：进 v1.1 清单
- ≤3：写进「不做清单」并注明原因

## 输出
- 一句话结论 + 排期影响（要挪走哪件事）。
```

## 10. `release-checklist` —— 发布检查

**什么时候用**：W24–W26，以及每次打包给别人玩。

**缺点**：清单会过时，每次发布要手动补新增项。

**模板**
```markdown
---
name: release-checklist
description: 打包与发布前必须逐项确认的清单。
---

## 必查
- [ ] 新存档能建、旧存档能读、坏档不崩
- [ ] 设置项重启后保留
- [ ] 联机：建房、加入、掉线、重连各一次
- [ ] 目标机型 1080p ≥45fps（记录实测值）
- [ ] 所有按钮有反馈，所有加载有提示
- [ ] 退出游戏不残留进程
- [ ] 截图 4 张 + 30 秒视频
- [ ] 商店页文字无 IP 风险词

## 输出
- 逐项打勾；未通过项直接给「改哪个文件/哪一步」。
```
